# ADR: Progressive Web App Implementation for Offline-First Deployment

Date: 2026-03-30
Status: Pending
Decision Maker: TBD

## Context

The ez-booth application is currently delivered as a browser-based Rust and WASM application.

The product already aligns well with a web-first architecture:

- the UI runs as a client-side rendered Leptos application
- operator data is stored locally in IndexedDB
- user preferences are stored in browser storage
- the application has no dependency on backend APIs or cloud services for core workflows
- existing validation already includes Chrome and Safari browser coverage

The current deployment model is workable on desktop browsers, but it is not yet sufficient for the desired field usage on iPad and iPhone.

The product needs to support operational use on:

1. iOS
2. Android
3. Windows
4. macOS

The most important new requirement is that the application must remain usable at the deployment site even when there is no internet connectivity.

This requirement is not optional.

The intended real-world flow is:

- prepare the application before the event
- make it available on operator devices such as iPad or iPhone
- use it during the event in an offline environment
- preserve local sales, vendor, and booth data safely on-device

The app already provides a strong base for this mode of operation.

### Existing Capabilities

- all primary business data is stored locally in IndexedDB
- booth, vendor, and purchase workflows already operate without backend round trips
- export and import capabilities already exist for backup and recovery workflows
- translations are bundled into the application at build time
- assets are produced as static files and can be served from a static host
- there are no external API calls required for checkout, reporting, or correction flows

### Current Technical Shape

The current build output is a static bundle generated by Trunk and includes:

- `index.html`
- bundled CSS
- bundled JavaScript loader
- a large WASM binary

The current architecture therefore already satisfies most of the technical prerequisites for an offline-capable Progressive Web App.

### Deployment Constraint

The deployment environment introduces an additional complication:

- internet access may be unavailable at the event site
- preloading the app before the event is possible
- a purely online hosting model is therefore insufficient on its own
- a fallback deployment path is desirable in case a mobile browser cache is cleared or becomes invalid

### iOS-Specific Concern

iOS Safari and installed web apps are usable for offline-first applications, but they have platform-specific constraints:

- service workers require HTTPS except for local development scenarios
- browser-managed caches may be evicted under system pressure or inactivity
- platform support differs from desktop browsers in subtle but important ways

This means the solution must not only support offline behavior in theory, but must also define a practical deployment and fallback strategy that acknowledges iOS behavior.

## Decision Drivers

- strong support for iPad and iPhone without requiring App Store distribution
- reliable offline use at the deployment site
- reuse of the existing web-first and local-storage-based architecture
- support across iOS, Android, Windows, and macOS with one product architecture
- low operational friction for non-technical operators
- low implementation risk relative to the current codebase
- avoidance of unnecessary native application packaging and release overhead
- clear fallback path if browser-managed offline state becomes unavailable

## Options Considered

### Option 1: Native iOS and Android Applications

#### Concept

Create dedicated native mobile applications for iOS and Android and distribute them through the Apple App Store and Google Play, or through enterprise or side-loading workflows where allowed.

The likely shape would be:

- maintain one or more native shells or full native frontends
- port or wrap existing business logic where practical
- store data locally on each device
- manage installation and updates through mobile app distribution mechanisms

#### Pros

- strongest native platform integration
- predictable install experience for mobile users
- access to native APIs and packaging models
- fewer browser-specific quirks once packaged and accepted by platform rules

#### Cons

- significantly increases implementation and maintenance scope
- introduces separate mobile packaging, signing, and release workflows
- requires Apple and Google ecosystem handling
- adds app review and policy overhead where store distribution is used
- weakens the current benefit of a single web-first product architecture
- does not directly improve desktop deployment because Windows and macOS would still need a separate solution

#### Platform Fit

- iOS: viable, but operationally expensive
- Android: viable, but operationally expensive
- Windows: not addressed by the mobile solution itself
- macOS: not addressed by the mobile solution itself

#### Outcome

Rejected. Native mobile applications would solve the install story at the cost of much higher product and release complexity, while still leaving desktop delivery as a separate concern.

### Option 2: Progressive Web App With Offline Caching

#### Concept

Keep the existing web application architecture and extend it into a Progressive Web App.

This would include:

- a web app manifest for installability
- iOS-compatible home screen metadata
- a service worker for asset caching and offline startup
- a small install guidance flow for operators
- static hosting or equivalent delivery for the initial load

The intended usage model is:

- the app is loaded once while connectivity is available
- static assets are cached locally
- the installed app launches from the home screen or browser without requiring a live backend
- booth data continues to live in IndexedDB on the device

#### Pros

- best reuse of the current architecture
- one implementation path for iOS, Android, Windows, and macOS
- no App Store dependency required
- aligns with the existing static deployment model
- preserves the current local-first data model
- keeps the product easy to build and ship from the current repository
- good fit for operators who only need install-once and run-offline behavior

#### Cons

- iOS imposes service worker and cache behavior constraints
- mobile install UX is less explicit than a native store-driven install flow
- some platform features available to native apps remain unavailable
- offline guarantees still depend partly on browser-managed storage behavior
- HTTPS is required for real service worker deployment outside local development

#### Platform Fit

- iOS: strong fit with known caveats
- Android: strong fit
- Windows: strong fit
- macOS: strong fit

#### Outcome

Selected. This option provides the best balance between deployment simplicity, platform coverage, offline capability, and alignment with the current codebase.

### Option 3: Native Wrapper Around the Existing Web App

#### Concept

Wrap the existing web application in a native shell such as Tauri, Capacitor, or Electron-derived tooling so the app can be distributed as a packaged application while still reusing web UI technology.

#### Pros

- keeps more existing web UI logic than a full native rewrite
- can expose native packaging and some native APIs
- may reduce some browser-specific limitations depending on wrapper choice

#### Cons

- introduces packaging complexity across multiple platforms
- still creates separate release artifacts per platform
- increases testing and support burden substantially
- provides more architecture than the current use case needs
- does not clearly outperform a well-implemented PWA for the current field workflow

#### Platform Fit

- iOS: possible, but higher release overhead
- Android: possible, but higher release overhead
- Windows: possible
- macOS: possible

#### Outcome

Rejected for now. This is a larger architectural shift than necessary for the immediate problem and should only be revisited if the browser-based deployment model proves insufficient after PWA rollout.

### Option 4: Continue With Browser-Only Access and Bookmarks

#### Concept

Leave the application as a normal browser-hosted site and instruct users to open it through Safari, Chrome, or another browser, optionally saving a bookmark.

#### Pros

- no implementation work required
- keeps deployment model unchanged
- lowest short-term effort

#### Cons

- poor mobile install experience
- no proper home-screen app identity
- no deliberate offline asset caching strategy
- browser UI remains visible and makes the app feel less dedicated
- higher user error risk because operators may reopen the wrong tab or stale bookmark state

#### Platform Fit

- iOS: technically usable, but not good enough
- Android: technically usable, but not good enough
- Windows: usable
- macOS: usable

#### Outcome

Rejected. This does not meet the offline-first product requirement with enough confidence and does not provide an intentional operator experience on mobile devices.

## Decision

Select Option 2: implement ez-booth as an offline-first Progressive Web App.

The selected approach will extend the current static WASM application with:

- a web app manifest
- iOS home-screen metadata
- a service worker
- aggressive caching of static assets, including the WASM bundle
- a lightweight in-app installation hint for operators

The product will continue to use its existing local-first storage architecture for business data.

The PWA work is a delivery and runtime enhancement, not a business-logic rewrite.

## Rationale

This option best matches the actual product needs and the current implementation strengths.

- The application already behaves like a local-first client application.
- The product already stores its operational data on-device in IndexedDB.
- The build output is already static and bundle-friendly.
- No backend dependency needs to be simulated for offline operation.
- A PWA can cover mobile and desktop platforms with one architecture.

The remaining challenge is not whether the application can work offline in principle. It already can.

The real challenge is ensuring that:

- users can install and launch it like an app
- static assets are retained for offline startup
- there is a pragmatic fallback when browser-managed caches are not dependable enough on all devices

PWA implementation addresses the first two directly, and the deployment strategy defined below addresses the third.

## Deployment Strategy

Adopt a hybrid deployment strategy.

### Primary Mode: Pre-Cached Deployment

The normal operational path is:

- open the application while internet connectivity is available
- load the full application bundle onto the device
- allow the service worker to cache required assets
- install the application to the device home screen where applicable
- run the app offline at the event site

This is the lowest-friction operator experience and should be the default path for iPad, iPhone, and Android devices.

### Fallback Mode: Local HTTPS Server

If an offline device cannot rely on retained cached assets, a local HTTPS-capable server may be used as a fallback.

The fallback concept is intentionally defined at a high level in this ADR.

The likely operational model is:

- prepare a local device such as a small laptop or Raspberry Pi-class machine
- host the static PWA bundle on a local network
- provide HTTPS so service worker behavior remains valid on mobile browsers
- allow client devices to load or refresh the app bundle from the local network when needed

This mode exists to mitigate the risk of browser cache eviction and to provide operational resilience when field devices need a controlled refresh path.

### Why Hybrid

The hybrid approach is selected because it avoids an all-or-nothing dependency on either model.

- pre-cached deployment keeps day-to-day operation simple
- a local server fallback reduces operational risk for longer events or devices with fragile cache retention
- the fallback can be introduced only where needed instead of making every deployment more complex

## Decisions Made

### App Delivery Model

Use a Progressive Web App rather than native packaging.

Rationale:

- strongest alignment with the existing architecture
- lowest additional maintenance cost
- one delivery model across all target platforms

### Offline Asset Strategy

Use a service worker with cache-first behavior for the application shell and versioned build artifacts.

Rationale:

- the app is a static bundle with hashed assets
- cache-first behavior is appropriate for offline startup
- the app should prefer reliable local launch over live asset fetches during operation

### WASM Caching Strategy

Aggressively cache the WASM bundle.

Rationale:

- the WASM artifact is large, but it is essential to app startup
- loading it once ahead of the event is acceptable
- avoiding a missing or delayed WASM fetch at the event site is more important than saving some storage

### Install UX

Provide a short built-in installation hint instead of a large tutorial flow.

Rationale:

- the user explicitly prefers a brief hint
- the install flow on iOS and Android is simple enough to explain with concise guidance
- a lightweight prompt keeps the product focused on operator work

### Branding for Initial Rollout

Use the existing `EZ Booth` name and allow temporary placeholder icons until final branding assets are available.

Rationale:

- avoids blocking the architectural work on final design assets
- keeps the first rollout practical
- supports later icon replacement without revisiting the core decision

## Technical Implementation Direction

The expected implementation will include the following pieces.

### Manifest

Add a `manifest.json` file that defines:

- app name and short name
- standalone display mode
- theme and background colors
- icon references
- scope and start URL

### HTML Metadata

Extend `index.html` with:

- manifest reference
- iOS web app capability metadata
- theme color metadata
- Apple touch icon references

### Service Worker

Add a service worker that:

- caches static assets required for startup
- serves cached assets first for offline reliability
- updates cached assets in the background when a new build is available
- treats the generated hashed assets as versionable cache entries

### Operator Install Guidance

Add a small install hint component in the UI that:

- briefly explains how to add the app to the home screen on iOS and Android
- can be dismissed
- does not interrupt core usage once acknowledged

### Build Integration

Update the build pipeline so that:

- manifest and icon assets are present in the final `dist/` output
- the service worker is available in the deployed static bundle
- future validation can confirm that installability and offline startup remain intact

## Consequences

### Positive

- a practical path to app-like installation on iPad, iPhone, Android, Windows, and macOS
- continued use of one product architecture and one codebase
- no App Store or native packaging dependency for the first rollout
- strong alignment with the current local-first storage design
- improved operator experience through home-screen launch and standalone display mode
- better resilience at internet-free deployment sites

### Negative

- offline startup still depends on correct service worker behavior and retained browser-managed storage
- iOS remains more constrained than desktop or Android in subtle ways
- HTTPS becomes a real deployment concern for anything beyond local development
- some deployment guidance and operator documentation will need to be written and maintained

### Neutral

- placeholder icons may be acceptable at first, but branding work will still be needed later
- some field teams may never need the local server fallback, while others may treat it as mandatory
- the exact fallback hosting stack can be decided later without changing this architectural decision

## Risks and Mitigations

### Risk: Mobile Browser Cache Eviction

If mobile browsers evict cached assets before or during an event, users may lose the ability to relaunch the app offline.

Mitigation:

- use aggressive initial caching
- document pre-event validation steps
- support a local HTTPS server fallback

### Risk: HTTPS Deployment Complexity

If operators need a local fallback server, HTTPS setup may be unfamiliar.

Mitigation:

- keep the ADR at the conceptual level
- produce a focused deployment guide during implementation
- avoid making local-server fallback mandatory for every deployment

### Risk: Install Flow Confusion on iOS

Users may not know how to add the app to the home screen.

Mitigation:

- provide a short in-app hint
- add a short operator guide in documentation

### Risk: Large Initial Bundle Download

The WASM file is large enough that the first load may take noticeable time.

Mitigation:

- preload and validate before the event
- cache aggressively so the cost is paid before field use
- treat this as an acceptable trade-off for robust offline launch

## Testing Strategy

Validation for this decision should include:

- installability checks on iOS Safari and Android Chrome
- offline startup checks after initial load
- regression validation of IndexedDB-backed workflows while offline
- cache refresh behavior when a new build is deployed
- confirmation that the app still works correctly in desktop browsers

The current browser validation workflow already provides a useful foundation, but PWA-specific validation steps will need to be added during implementation.

## To Be Decided

The following implementation details remain open and should be decided during delivery planning:

- the exact icon asset set and final branded artwork
- whether the local fallback server is optional guidance or part of the standard deployment kit
- the exact wording and placement of the operator install hint
- whether update activation should be fully automatic or partially user-visible
- what level of deployment documentation is needed for non-technical event operators

These questions do not change the architectural choice of a PWA. They refine how the chosen approach will be delivered.

## Next Steps

1. create a focused implementation plan for manifest, service worker, install hint, and build integration
2. define the offline validation checklist for iOS and Android devices
3. document the pre-event preload workflow for operators
4. prepare the local HTTPS fallback guidance as a separate implementation document if needed
5. replace placeholder icons with final branded assets when available
